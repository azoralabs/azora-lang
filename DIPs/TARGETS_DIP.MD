# Azora Targets and Toolchain - DIP Implementation Profile

> Status: **decided** (roadmap A6, 2026-11-07). Qualified today:
> `arm64-apple-macosx` natively (LLVM, linked by the host's clang) and
> WebAssembly under Node (the test harness); the interpreter everywhere the
> JVM runs. The other triples of §1 are the plan, each counted as supported
> only when CI builds and runs on it (§3).

Which machines Azora programs run on, what builds them, and how a program gets
into a browser.

---

## 1. Target triples

| Triple | OS | Graphics (Engine) | Notes |
|---|---|---|---|
| `arm64-apple-macosx` | macOS on Apple silicon | Metal | Qualified today. |
| `x86_64-apple-macosx` | macOS on Intel | Metal | |
| `arm64-apple-ios` | iOS, iPadOS | Metal | Device; `arm64-apple-ios-simulator` for the simulator. |
| `aarch64-linux-android` | Android (arm64-v8a) | Vulkan, GLES 3 | |
| `x86_64-pc-windows-msvc` | Windows x64 | DX12, Vulkan | |
| `aarch64-pc-windows-msvc` | Windows on Arm | DX12, Vulkan | |
| `x86_64-unknown-linux-gnu` | Linux x64 | Vulkan, GLES 3 | |
| `aarch64-unknown-linux-gnu` | Linux arm64 | Vulkan, GLES 3 | |
| `wasm32-unknown-unknown` | Browsers, and Node for tests | WebGPU, WebGL 2 | The in-house WebAssembly backend (§4). |

The compiler does not pin a triple in the LLVM module yet (`LlvmCodegen`):
the module is compiled for the machine that links it. Building for another
triple needs the triple written into the module, a data layout, and a
target-specific runtime. Until then `azora build`, `run` and `test` refuse
`--target` with a diagnostic rather than building for the host under another
name.

## 2. The toolchain (decision D-1)

The rule that Azora uses no third-party code (roadmap principle 1) is about what
**ships inside a program**: the runtime, std, the Engine and Studio are Azora
calling the OS and the GPU driver. It does not cover the tools that build a
program, which stay build-time tools:

- LLVM (the compiler emits LLVM IR) and `clang`, which compiles it and links;
- the system linker;
- the platform's packaging and signing tools (Apple's code signing, Android's
  packaging), as Track B needs them;
- `git`, which the package manager runs for git dependencies (PACKAGES_DIP §3.1).

Nothing of them is linked into a program. Replacing any of them (an Azora code
generator, linker or packager) is possible later work, not a requirement.

## 3. What "supported" means

A triple is supported when CI, on that triple or an emulator of it, builds the
compiler's conformance programs and runs them with the expected output, and for
the Engine renders the reference scenes (roadmap B8). A triple that is in §1
but not yet qualified is reported as such by the CLI; it never silently falls
back to the host.

## 4. The web path

Web programs are built by the compiler's own WebAssembly backend
(`WasmCodegen`), not through LLVM's: it is brought to parity with the LLVM
backend - every construct behaves the same, or is a named compile error on
WebAssembly. The browser side is generated by Azora as well: the host imports a
module needs (BRIDGE_DIP §5.3) are emitted with it as JavaScript glue, so no
hand-written or third-party loader is involved. WebGPU and WebGL 2 are reached
through those imports.

The earlier compile-to-JavaScript target is gone, and with it the website's
in-browser compiler bundle. A browser playground returns when a compiler runs
on WebAssembly: the Azora compiler (roadmap Track E), or a Kotlin/Wasm build of
this one - its `webMain` sources exist, but no Gradle target builds them.

## 5. Platform services (decisions D-2 and D-4)

- **TLS**: where the OS provides TLS - Apple's platforms and Windows - programs
  use it through the OS's API. On Linux and Android, TLS 1.3 and its primitives
  are written in Azora, with published test vectors, constant-time review and
  fuzzing (roadmap B11).
- **Store purchases and ad networks** stay out of the Engine. An OS framework
  such as StoreKit may be bridged like any other; a vendor client library
  (Google Play Billing, an ad network's SDK) is a project's own choice and never
  part of an Engine package.

## 6. Shaders (decision D-3)

The Azora shader compiler emits each backend's form itself: MSL for Metal,
SPIR-V for Vulkan, WGSL for WebGPU, GLSL ES for GLES, and **DXIL** for DX12 -
no Windows shader compiler is involved, and Shader Model 6 features are
available.
